# Customer account interface

Customer accounts use the existing AssayNova brand and four exact SPA routes: `/account`, `/login`, `/register`, and `/recover-account`. Each has a distinct static view/heading. The server capability meta `assaynova-accounts=enabled` enables the client and global My account entries; static-only mode has no browser-authentication fallback. Public COA lookup remains available without sign-in.

The account client is lazy: importing/constructing it does not read storage or make network requests. Account/auth/request views bootstrap the session only when needed. All API calls use same-origin credentials, no-store, fixed `/api/account` endpoints and an in-memory CSRF token. User/error responses are validated; the UI never renders raw API error messages. Known API error codes are normalized and select static feedback before generic HTTP-status fallbacks, including duplicate signup, rejected credentials/recovery, the 50-draft limit and revision conflict. Password validation preserves spaces and Unicode and matches the 15–128-codepoint / 512-byte rule. Email is limited to 160 characters, name 100 and company 160. Email remains immutable and unverified; no report ownership is inferred from it.

Signup, password recovery and recovery-code replacement show eight codes in a private one-time pane. The user deliberately copies them (with a selectable manual fallback) and acknowledges saving them before continuing. Codes/passwords/tokens are never persisted in browser storage, URLs, history or toast messages. Navigation/logout clears code DOM and controller memory; late clipboard outcomes cannot restore it. Report recovery through Nova Support is a different, unchanged local-draft flow.

## Request drafts

- Guest/device drafts retain the existing key, 50-record cap, exact read-back and explicit Save behavior. Contact and Support drafts are unchanged. No local drafts are enumerated or uploaded during sign-in, registration, account-page entry or privacy choices.
- A confirmed signed-in new request defaults to Account. This device remains an explicit alternative. Resuming a device draft keeps that destination. Account saves never fall back to device storage on network, session or revision failure.
- Cloud save waits for a validated returned document. Server opaque ID/revision/owner guard are separate from the strict v2 record and its display reference. The first new cloud intent freezes its idempotency key, reference, timestamp and canonical payload together before POST. An uncertain response retains this tuple in memory. Retry first replays that exact create; if the user edited meanwhile, it then PUTs the newest valid state to the acknowledged document/revision. It does not mint another create/reference/timestamp.
- Same-user sign-in can resume that pending intent. A different user or explicit logout clears/withholds the prior account-bound editor; account A's response cannot paint or upload into account B. Navigation aborts the UI operation, clears private DOM and revokes local image previews, without claiming that an abort undid a server write. Unsaved state/pending intent remain in bounded controller memory for a safe retry.
- Account request drafts are not laboratory submissions or sent emails. List/detail reads capture the displayed account owner before refreshing the session, check that owner before GET and again after GET, and discard changed-owner results before painting. Delete also checks the captured owner before its session-bound CSRF mutation. Owner change notifications clear the previous private view. Email/name matching never attaches reports.
- Device detail offers explicit Save to account, opening the selected draft for review and final account Save. Its stable import key is based on the local reference and scoped by the server's authenticated owner. Original device records remain. An older unversioned draft uses Open as new draft: validate/copy known fields into a new editable v2 request, require final Save, retain the old record/unknown fields unchanged, and never post v1 directly.

All private account/profile/code/draft regions reuse `data-request-private`; existing development copy redaction therefore applies without a new selector. New module-generated descendants have no fabricated original-template annotations. Titles/H1s contain no user values. Account redirects accept only exact `/account` or `/submit-sample` destinations. Normal navigation/history and keyboard focus continue through the existing app router.

Necessary session and CSRF cookie inventory is documented in both regular and fallback privacy views. The customer cookie prefix cannot be configured as optional cleanup storage. Optional consent and existing draft keys/receipts are not changed by account use.

Focused unit coverage uses injected transports/DOM/storage, including lost acknowledgements, revision failures, owner changes, pending duplicate prevention, code cleanup, redaction, safe returns, explicit conversion and retained guest behavior. Additional synthetic HTTP fixtures exercise real uppercase errors, the 50-draft limit, owner switches before/during list/detail reads, discarded private UI results and delete guards. Backend durability/security and native responsive account flows are separate coordinated gates.
